# Развёртывание флота

[English](fleet.md) | **Русский**

Четыре площадки, один бинарник. Роль выбирается подкомандой, всё остальное —
теми же флагами, что и у одиночного прогона.

```
onion-gen -F test -d ./keys                       # одиночный прогон
onion-gen master --listen :8080 --store ./keys    # оркестратор
onion-gen worker --master http://master:8080      # работник
```

## Что нужно решить на любой площадке

**Где мастер.** Работник ходит к нему сам и входящих соединений не принимает,
так что известный адрес нужен только мастеру. На практике это оказалось не
теорией: при проверке на двух машинах маршрутизация между ними была
односторонней, и флот собрался только потому, что инициатива на стороне
работника.

**Где хранилище мастера.** Это единственное, чья потеря необратима: адрес
найдётся второй раз не скоро. Том, а не слой контейнера.

**Папки или база.** `--store` делает папку на каждый ключ, `--db
./keys/fleet.db` вместо этого пишет строки, и в строках те же байты, что и в
файлах. Папок проходит около 160 в секунду, строк — 206 000, поэтому на коротком
фильтре от этого выбора зависит, будут ли работники стоять в очереди. Один файл
к тому же проще положить на том и забрать в резервную копию, чем миллион папок.

**Буфер работника.** Находки, которые мастер не успел принять, лежат у
работника до подтверждения. В обычной работе он пуст; том нужен, чтобы
перезапуск посреди недоступности мастера их не унёс.

**Длина фильтра.** Флот не возьмёт фильтр короче четырёх символов. Но четыре —
это порог, а не достаточность: одна RTX 4060 на четырёхсимвольном фильтре даёт
954 находки в секунду, а хранилище из папок принимает около 160. Программа
считает ожидаемую частоту при запуске и говорит её вслух — для того хранилища,
которое ей задали: база 954 в секунду берёт с запасом.

## Docker Compose — проверено

```bash
docker build -t onion-gen:latest .
docker compose up -d --scale worker=3
```

Файлы — [`Dockerfile`](../../Dockerfile) и
[`docker-compose.yml`](../../docker-compose.yml) в корне. Образ собирается сам:
первая ступень компилирует, вторая содержит только бинарник на distroless —
ни оболочки, ни пакетного менеджера, ни утилит.

CI берёт не его. Он собирает бинарники один раз через zig, а потом упаковывает
их [`Dockerfile.dist`](../../Dockerfile.dist), в котором ступени компиляции нет
вовсе. Образ выходит тот же; разница только в том, компилируются исходники
здесь или уже скомпилированы.

Собрать под обе архитектуры или прогнать тесты внутри образа:

```bash
docker buildx build --platform linux/amd64,linux/arm64 .
docker build --target check .
```

Компиляция всегда идёт на архитектуре сборщика и кросс-компилирует через zig, а
не под эмуляцией: эмулированная сборка этого крейта занимает почти час и даёт
те же байты.

Готовые образы публикуются в `ghcr.io`: `latest` с ветки main и версия по тегу.

Проверено на живой машине (x86_64, 8 ядер): три работника по 38.3 блока в
секунду, 115 суммарно; масштабирование до пяти дало 198; ноль отказов; пробы
`/health` отвечают 200 изнутри сети контейнеров.

**Остановка**: `docker compose down`. **Масштаб**: `--scale worker=N`.

Две подробности, найденные проверкой, а не вычитанные:

*Убитый работник возвращается, остановленный — нет.* `restart: unless-stopped`
поднимает контейнер после настоящего отказа, но `docker kill` и `docker stop`
Docker считает решением оператора и намеренно не отменяет. То есть «работник
упал» и «работника остановили» ведут себя по-разному, и это правильно.

*Без политики перезапуска флот тихо усыхает.* В первой редакции
`docker-compose.yml` её не было: аренда убитого работника возвращалась, как
задумано, а брать её было некому.

## Kubernetes — чарт написан, **в кластере не проверен**

Чарт лежит в [`charts/onion-gen`](../../charts/onion-gen).

```bash
helm install fleet charts/onion-gen \
  --set filters={abcdef} \
  --set worker.replicas=10 \
  --set master.persistence.size=50Gi
```

Что проверено без кластера: `helm lint --strict` проходит для обоих вариантов
работника, шаблоны рендерятся, YAML разбирается, защита по длине фильтра
срабатывает при установке (`filters={abc}` даёт отказ с объяснением), а в
отрендеренном подтверждено главное — у работника нет ни `--filter`, ни
`--limit`, живость на `/health`, готовность на `/ready`, мастер пересоздаётся,
а не катится.

Чего **не** проверено: ничего из этого не разворачивалось. Кластера нет ни на
одной доступной машине, и пока он не появится, всё ниже — описание, а не отчёт.

Два значения, которые стоит задать осознанно:

`master.seed.existingSecret` — без него мастер берёт случайное семя и говорит
об этом: такой поиск не продолжить после замены мастера. Семя так же
чувствительно, как сами ключи, поэтому оно в `Secret` и приходит через
окружение, а не через командную строку: аргументы процесса видны всему, что
умеет перечислять процессы на узле.

`worker.kind` — `Deployment` держит буфер несданных находок в `emptyDir`, и
замена пода во время недоступности мастера их унесёт. `StatefulSet` даёт
каждому работнику свой том и устойчивое имя в сводке флота.

Работники поднимаются **`Deployment` с репликами, а не `Job`**: реплика не
завершается, она работает, пока её не остановят, а решение о том, что найдено
достаточно, принимает человек, глядя на хранилище мастера.

| | |
|---|---|
| мастер | `Deployment` на одну реплику плюс `Service` — имя службы и есть адрес для работников |
| хранилище | `PersistentVolumeClaim` на мастере |
| работники | `Deployment`, `replicas: N`; тома не нужны, кроме буфера |
| остановка | `kubectl scale --replicas 0` или удаление |
| метрики | `/metrics` у мастера и у каждого работника, по отдельной цели для сбора |

Пробы — главное, что здесь надо настроить правильно:

```yaml
livenessProbe:
  httpGet: { path: /health, port: 9100 }
  periodSeconds: 30
readinessProbe:
  httpGet: { path: /ready, port: 9100 }
  periodSeconds: 10
```

**Живость не зависит от достижимости мастера, и менять это нельзя.** Работник,
у которого мастер пропал, занят делом: досчитывает взятый диапазон и копит
несданные находки. Если живость будет зависеть от мастера, его падение
перезапустит разом весь флот и выбросит и то и другое — сбой одного компонента
превратится в потерю работы всеми. Проверено на живом прогоне: мастер убит,
`/health` отвечает 200, `/ready` — 503, работник продолжает работать.

Одна ловушка: **не давайте работнику `-n`**. Достигнув предела, он выйдет с
нулём, а `Deployment` поднимет его снова — и так без конца. Предел осмыслен для
одиночного прогона, не для реплики.

## Docker Swarm — не проверено

То же, что и Compose, с заменой на `docker service`:

```bash
docker service create --name master --publish 8080:8080 \
  --mount type=volume,source=keys,target=/home/nonroot/keys \
  onion-gen:latest -F abcde master --listen 0.0.0.0:8080 --store /home/nonroot/keys
docker service create --name worker --replicas 5 \
  onion-gen:latest --compute cpu worker --master http://master:8080
```

**Остановка**: `docker service rm`. **Масштаб**: `docker service scale worker=N`.

## Голые виртуальные машины — не проверено как служба

Связка двух машин проверена напрямую, без systemd: мастер на одной, работники
на обеих, 337.4 блока в секунду суммарно против 153.5 у одной, 114 находок и ни
одного дубликата.

Как служба это выглядит так:

```ini
[Unit]
Description=onion-gen worker
After=network-online.target

[Service]
ExecStart=/usr/local/bin/onion-gen --compute auto -d /var/lib/onion-gen \
          worker --master http://master.example:8080
Restart=always
# Прерванный прогон выходит кодом 4, и для работника это нормальный исход:
# перезапускать надо в любом случае.
RestartSec=5
User=onion-gen

[Install]
WantedBy=multi-user.target
```

**Остановка**: `systemctl stop onion-gen-worker`.

## Коды возврата

| код | что значит |
|---:|---|
| 0 | прогон достиг заданной цели |
| 1 | не удалось начать |
| 2 | ошибка в командной строке |
| 3 | найденный ключ не открыл свой адрес — дефект, прогон остановлен |
| 4 | прогон остановлен до достижения цели |

Нулём заканчивается **только** достигнутая цель. Это не формальность: будь
прерывание нулём, вытесненный под засчитывался бы успехом, и `Job` с одним
требуемым завершением снял бы весь флот, не найдя ни одного ключа.
