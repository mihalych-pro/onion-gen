# Как применить сгенерированную пару ключей

[English](using-generated-keys.md) | **Русский**

Что делать с каталогом `<адрес>.onion/`, который выдал генератор, чтобы он стал
работающим onion-сервисом.

Здесь — только эксплуатация.

## Что из трёх файлов нужно

```
<адрес>.onion/
├── hs_ed25519_secret_key    ← единственный обязательный
├── hs_ed25519_public_key    ← tor восстановит сам
└── hostname                 ← tor восстановит сам
```

Достаточно одного `hs_ed25519_secret_key`: при старте tor выведет из него
публичный ключ и адрес и перезапишет два других файла. Копировать весь каталог
всё равно удобнее — так видно, какой адрес ожидается, и расхождение сразу
заметно.

Обратное неверно: `hs_ed25519_public_key` без секретного ключа бесполезен.

## Вариант 1: постоянный сервис через файлы

### 1. Положить ключи

```bash
sudo cp -r abcd1234….onion /var/lib/tor/myservice
sudo chown -R _tor:_tor /var/lib/tor/myservice   # Debian/Ubuntu: debian-tor
sudo chmod 700 /var/lib/tor/myservice
sudo chmod 600 /var/lib/tor/myservice/hs_ed25519_secret_key
```

Имя пользователя tor различается: `debian-tor` в Debian и Ubuntu, `tor` в
Fedora и Arch, `_tor` в OpenBSD и macOS/Homebrew. Проверить —
`ps -o user= -C tor` или в unit-файле службы.

Права обязательны: tor **откажется** запускаться, если каталог сервиса доступен
кому-то кроме владельца. Это не придирка — каталог содержит ключ, дающий полный
контроль над адресом.

### 2. Прописать в `torrc`

```
HiddenServiceDir /var/lib/tor/myservice
HiddenServicePort 80 127.0.0.1:8080
```

`HiddenServicePort <порт_в_сети_Tor> <куда_проксировать>`. Слева — порт, по
которому сервис виден снаружи; справа — локальный адрес вашего приложения.
Строк `HiddenServicePort` может быть несколько для одного каталога.

Приложение должно слушать именно на `127.0.0.1`: если оно слушает `0.0.0.0`, оно
одновременно доступно и напрямую, что сводит на нет смысл onion-сервиса.

### 3. Перезапустить и проверить

```bash
sudo systemctl reload tor        # или restart
sudo cat /var/lib/tor/myservice/hostname
```

Выведенный адрес **обязан** совпасть с именем каталога, который дал генератор.
Если не совпал — tor взял другой ключ: чаще всего каталог был не пуст и tor
сгенерировал новый ключ при первом запуске, а ваш файл положили уже после.

Логи при проблемах:

```bash
sudo journalctl -u tor -n 50
```

## Вариант 2: без файлов, через ControlPort

Подходит для эфемерных сервисов и для приложений, которые управляют tor сами.

Команда `ADD_ONION` принимает секретный ключ в base64 — **без** 32-байтового
файлового префикса, то есть ровно 64 байта:

```
ADD_ONION ED25519-V3:<base64 64 байт> Port=80,127.0.0.1:8080
```

Такую строку выдаёт генератор в режиме `-y --rawyaml` (поле
`hs_ed25519_secret_key`) — это тот же формат, преобразовывать ничего не нужно.

> **Порядок аргументов.** `--rawyaml` нужно ставить **до** `-Y`: ключ `-Y`
> забирает следующие аргументы как имя файла и адрес, поэтому
> `-Y file.yaml --rawyaml` приводит к ошибке `bad onion argument length`.
> Правильно: `--rawyaml -Y file.yaml`.

Получить её из уже существующего файла:

```bash
tail -c 64 hs_ed25519_secret_key | base64 -w0
```

`tail -c 64` отрезает 32-байтовый префикс. На macOS у `base64` нет `-w0`, но он
и не переносит строки по умолчанию.

Пример через `nc` (ControlPort должен быть включён в `torrc`):

```bash
printf 'AUTHENTICATE ""\r\nADD_ONION ED25519-V3:%s Port=80,127.0.0.1:8080\r\nQUIT\r\n' \
  "$(tail -c 64 hs_ed25519_secret_key | base64)" | nc 127.0.0.1 9051
```

В ответе придёт `250-ServiceID=<адрес без .onion>` — он должен совпасть с
именем каталога.

Такой сервис живёт, пока держится управляющее соединение (или до `DEL_ONION`),
и **не** сохраняется на диск. Добавьте флаг `Detach`, если сервис должен
пережить закрытие соединения.

## Вариант 3: контейнер

```dockerfile
# Ключи НЕ копируются в образ — только монтируются на запуске.
FROM alpine
RUN apk add --no-cache tor
COPY torrc /etc/tor/torrc
USER tor
CMD ["tor", "-f", "/etc/tor/torrc"]
```

```bash
docker run --rm \
  -v "$PWD/abcd1234….onion:/var/lib/tor/myservice:ro" \
  myimage
```

Каталог монтируется, а не встраивается: секретный ключ в слое образа
расползётся по всем, кто этот образ вытянет, и останется в истории реестра даже
после «удаления».

В Kubernetes ключ — это `Secret`, смонтированный с `defaultMode: 0600`, а не
`ConfigMap` и не переменная окружения.

Готовый рабочий пример связки tor + nginx через `docker compose` лежит в
[`examples/docker-onion-nginx/`](../../examples/docker-onion-nginx/) — там же
инструкция по запуску.

## Отдача сайта через nginx

Типовая связка: tor слушает виртуальный порт onion-сервиса и проксирует на
локальный nginx, nginx отдаёт сайт.

### torrc

```
HiddenServiceDir /var/lib/tor/myservice
HiddenServicePort 80 127.0.0.1:8080
```

### nginx

Отдельный `server`-блок, привязанный к порту из `HiddenServicePort`, и
`server_name` с onion-адресом:

```nginx
server {
    listen 127.0.0.1:8080;
    server_name abcd1234….onion;

    root /var/www/myservice;
    index index.html;

    # Клиент уже внутри Tor: шифрование и аутентификация адреса обеспечены
    # самим протоколом onion-сервиса. TLS здесь не нужен и только добавит
    # проблем с сертификатом на .onion-имя.

    # Сообщить браузеру Tor, что у сайта есть onion-версия, можно и с
    # клирнет-домена — но заголовок ставится ТАМ, а не здесь:
    # add_header Onion-Location https://abcd1234….onion$request_uri;

    location / {
        try_files $uri $uri/ =404;
    }
}
```

Слушать строго на `127.0.0.1:8080`, а не на `0.0.0.0:8080`: иначе тот же
контент доступен напрямую по IP сервера, и связь между onion-адресом и вашим
сервером устанавливается тривиально.

### Если nginx проксирует на приложение

```nginx
server {
    listen 127.0.0.1:8080;
    server_name abcd1234….onion;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto http;

        # НЕ передавайте реальный IP: у onion-клиента его нет, а $remote_addr
        # здесь всегда 127.0.0.1 — заголовок только создаст ложное ощущение,
        # что вы знаете источник запроса.
    }
}
```

### Чего не делать

- **Не редиректить с onion на клирнет-домен.** Это выкидывает пользователя из
  Tor и раскрывает его. Частая причина — общий `server`-блок с
  `return 301 https://example.com$request_uri` как дефолтный.
- **Не ставить TLS-сертификат на .onion ради «замочка».** Соединение уже
  аутентифицировано адресом. Обычные CA такие сертификаты не выдают (кроме
  редких EV), а самоподписанный даст пользователю предупреждение.
- **Не включать HSTS на onion-домене** и не наследовать его из общего конфига:
  политика привяжется к имени и сломает доступ при смене схемы.
- **Не отдавать одинаковый `Server`/`ETag`/баннеры на клирнете и в onion** —
  это связывает два адреса между собой.
- **Не логировать в общий access.log вместе с клирнет-трафиком**, если цель —
  не связывать эти два сервиса. Отдельный `access_log` для onion-блока.

### Проверка

```bash
sudo nginx -t && sudo systemctl reload nginx
curl -s -H 'Host: abcd1234….onion' http://127.0.0.1:8080/ | head
```

Локальный `curl` проверяет, что nginx отвечает нужным виртуальным хостом.
Проверка снаружи требует Tor-клиента:

```bash
curl --socks5-hostname 127.0.0.1:9050 http://abcd1234….onion/
```

## Проверка без запуска сервиса

Убедиться, что ключ соответствует адресу, можно не поднимая tor:

```bash
./scripts/verify/verify-onion-address.py <каталог>.onion
```

Скрипт считает адрес из публичного ключа и, кроме того, проверяет, что
секретный ключ действительно даёт этот публичный ключ. Отключить вторую проверку
(она медленная) — флагом `--no-secret`, проверить все каталоги, а не первые
двенадцать — флагом `--all`.

## Что из этого проверено

| Утверждение | Статус |
|---|---|
| `base64(hs_ed25519_secret_key[32:])` — ровно 64 байта и совпадает с полем `--rawyaml` | проверено |
| `tail -c 64 … \| base64` даёт ту же строку, что нужна `ADD_ONION` | проверено |
| Round-trip `-y --rawyaml` → `--rawyaml -Y` восстанавливает ключ, адрес сходится | проверено |
| `--rawyaml` обязан идти до `-Y` | проверено (воспроизведена ошибка) |
| tor выводит адрес из одного лишь `hs_ed25519_secret_key` | проверено |
| Адрес от tor совпадает с адресом от генератора | проверено |

Последние два пункта проверены на tor 0.4.9.12 без выхода в сеть: в каталоге
сервиса оставлен **только** `hs_ed25519_secret_key`, tor запущен с
`DisableNetwork 1`, после чего он сам создал `hs_ed25519_public_key` и
`hostname`:

```
$ ls /tmp/tortest/hs        # до запуска
hs_ed25519_secret_key

$ tor -f torrc              # DisableNetwork 1 — дескриптор не публикуется
[notice] DisableNetwork is set. Tor will not make or accept non-control
         network connections.

$ cat /tmp/tortest/hs/hostname
a6k4fysykhkhkob5uhfrooihjdkgoriodvtydtcdgnnwolzzvxvlnyqd.onion   ← совпал
```

Это подтверждает и то, что из трёх файлов обязателен только секретный ключ.

Попутно: tor выставляет **всем** файлам в каталоге режим `0600` — строже, чем
генератор, который оставляет публичный ключ и `hostname` доступными на чтение.
Он также создаёт подкаталог `authorized_clients/` для клиентской авторизации.
Не пугайтесь изменившихся прав и лишнего каталога — это нормальная работа tor,
а не повреждение ключей.

Проверка не потребовала публикации сервиса в сеть Tor: флаг `DisableNetwork 1`
останавливает tor до объявления дескриптора.

## Onionbalance

Onionbalance принимает обычный `hs_ed25519_secret_key` как ключ фронтенда, так
что сгенерированный адрес можно использовать как точку входа для набора
бэкендов. Формат ключа тот же — отдельной подготовки не требуется.

## Чего делать нельзя

- **Переиспользовать один ключ для разных сервисов.** Адрес — это и есть
  публичный ключ; два сервиса на одном адресе неразличимы для клиента и
  связывают ваши сервисы между собой.
- **Класть секретный ключ в git, образ контейнера или ConfigMap.** Кто получил
  файл — получил адрес навсегда; отозвать его нельзя, только сменить.
- **Генерировать ключи на чужой машине или через веб-сервис.** Владелец машины
  видит ключ.
- **Полагаться на ключи, сгенерированные из пароля, для несвязанных сервисов.**
  Ключи из одного пароля связаны: утечка одного помогает восстановить соседние.
- **Оставлять резервную копию без шифрования.** Бэкап каталога сервиса — это
  бэкап полного контроля над адресом.

## Смена ключа

Отозвать скомпрометированный адрес невозможно — можно только перестать им
пользоваться. План: сгенерировать новый адрес, поднять оба параллельно,
объявить переезд, через время выключить старый. Клиенты, знающие только старый
адрес, будут потеряны — поэтому ключ и стоит беречь.
