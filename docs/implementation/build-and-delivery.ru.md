# Сборка и доставка

[English](build-and-delivery.md) | **Русский**

Одна машина собирает под все три платформы; остальные получают бинарники, а не
исходники.

## 1. Что нужно

На машине сборки:

- Rust через `rustup`, не ниже версии из `rust-version` в `Cargo.toml`.
- `zig` и `cargo-zigbuild` (`brew install zig cargo-zigbuild`). zig даёт
  компоновщик и libc под каждую цель, больше ничего не требуется.
- `go-task` (`brew install go-task`), чтобы запускать задачи по имени.
- Цели: `task cross:setup`.

На целевых машинах — ничего. В этом и смысл.

## 2. Почему zig, а не альтернативы

`mingw-w64` и zig — не равные варианты: zig содержит mingw-w64 для своей
windows-цели и сверх того даёт Linux с нижней границей версии glibc. Один
mingw закрыл бы половину задачи.

`cross` работает через Docker, которого на машине сборки не было запущено, а на
macOS это ещё и виртуальная машина с медленным доступом к файлам — прямая
противоположность быстрому локальному циклу. Он остаётся лучшим ответом там,
где нужна побитовая повторяемость с CI.

zig линкует через lld, не требует контейнера и не мешает кешированию cargo.

## 3. Сборка

```bash
task cross:all        # все три платформы
task cross:linux      # x86_64-unknown-linux-gnu.2.28
task cross:windows    # x86_64-pc-windows-gnu
task cross:macos      # aarch64-apple-darwin
```

Суффикс `.2.28` у linux-цели — это самая старая версия glibc, на которой
бинарник пойдёт; он часть имени цели, а не отдельный ключ.

Читается это наоборот интуиции: совместимость у glibc обратная, но не прямая,
так что собранное против новой версии на старой не запустится. Линковщик пишет
рядом с каждым взятым символом версию — `memcpy@GLIBC_2.14`, а не `memcpy` — и
берёт самую новую, какую даёт машина сборки. zig вместо этого подкладывает свои
заголовки и заглушки и держит все символы не выше указанной границы. Отсюда:
чем ниже цифра, тем шире охват, а поднятие только отрезает дистрибутивы. 2.28 —
это RHEL 8 и его пересборки, поддержка до мая 2029; ничего старше обновлений
уже не получает.

Все три собраны на `darwin/arm64` и запущены каждая на своей машине: linux на
Debian 13, windows на Windows 11 вне WSL, macos обратно на Apple Silicon.
Каждая сама определила AVX2 или NEON и нашла адрес.

**Linux тоже собирает все три**, включая неочевидную цель под macOS: zig несёт
заглушки libc для macOS и подписывает результат ad hoc, без чего Apple Silicon
бинарник бы убила. Поэтому одного раннера достаточно, чтобы выпустить все
артефакты, — что важно там, где раннеров под Windows и macOS нет.

## 4. Доставка

```bash
task ship:linux
task ship:windows
```

Адреса машин берутся из окружения или локального `.env`, который закрыт
`.gitignore`. Каждая задача кладёт бинарник в отдельный каталог на удалённой
машине и там же его запускает, так что успешная задача означает работающий
бинарник, а не просто скопированный.

Отдельный каталог здесь не прихоть: доставка под голым именем `onion-gen`
столкнулась с одноимённым каталогом исходников, и `scp` записал бинарник
внутрь него.

## 5. Тесты под Windows без установки Rust

`cargo zigbuild --release --tests --target x86_64-pc-windows-gnu` собирает
тестовые исполняемые файлы; их достаточно скопировать и запустить. Так нативно
проходят 109 тестов.

Один тест запуститься не может: `end_to_end` зовёт Python-верификатор по пути,
зашитому при сборке, а на другой машине его там нет. Теперь он пропускается с
сообщением вместо падения, и сообщение именно печатается, а не проглатывается
— тест, который молча ничего не проверяет, хуже падающего.

## 6. Непрерывная интеграция

`.github/workflows/ci.yml` прогоняет форматирование, clippy и тесты нативно на
Linux, Windows и macOS и собирает бинарники на одном linux-раннере — кроме
macOS, которые собираются на маке, потому что `wgpu` линкует фреймворки Apple,
живущие только в их SDK. `.gitlab-ci.yml` делает остальное только на
linux-раннерах, что возможно как раз потому, что zig собирает оттуда любую цель.

Обе конфигурации собирают CUDA-ядро отдельным заданием и передают PTX ниже
артефактом. Каждое следующее задание выставляет `ONION_GEN_KERNEL_PTX` и потому
остаётся на stable; без этого build-скрипт собирал бы ядро заново в каждом
задании — один и тот же PTX несколько раз и столько же шансов получить разный.

Образ не компилируется заново, а упаковывается из бинарников: оба пайплайна
собирают все шесть один раз через zig, а потом отдают два linux-овых
`Dockerfile.dist`, в котором ступени компиляции нет. `Dockerfile` по-прежнему
собирает из исходников и нужен для локальной сборки. В обоих случаях обе
архитектуры получаются с одного amd64-раннера без эмуляции — единственные
стадии, которые что-то выполняют, закреплены за `$BUILDPLATFORM`, а публикуемая
только копирует файлы.

На GitHub это buildx, на GitLab — rootless BuildKit через
`buildctl-daemonless.sh`, которому не нужен ни привилегированный раннер, ни
docker-in-docker. Обе подписывают опубликованный образ по digest через cosign,
без ключа.

Workflow для GitHub прогонялись. **`.gitlab-ci.yml` — нет**: удалённого на
GitLab пока не существует, так что это корректный YAML и не более. И учтите:
подпись без ключа там требует gitlab.com — self-managed инстанс Fulcio как
издателя не признаёт, и задание либо переходит на ключ, либо пропускается, как
описано в его комментариях.

Одна деталь, которая иначе укусит: официальный образ `cargo-zigbuild`
закрепляет тулчейн старее того, что требует манифест, поэтому каждое задание
сперва ставит stable.

## 7. Версии, на которых это делалось

zig 0.17.0, cargo-zigbuild 0.23.4, rustc 1.99.0, go-task из Homebrew.

**Пара версий связана жёстче, чем кажется.** Нынешний Rust при линковке под
aarch64 выдаёт `--fix-cortex-a53-843419`, и отбрасывает этот аргумент
`cargo-zigbuild`, а не zig. С версией 0.20.1 сборка под arm64 падает с
`unsupported linker arg`, под amd64 проходит — то есть ломается половина целей,
и только одна. Отсюда точное закрепление обеих версий в образе и в CI.

Официальный образ `cargo-zigbuild` сейчас несёт zig 0.16.0, Rust 1.93.0 и
cargo-zigbuild 0.23.4 — проверено запуском, а не по документации. GitLab берёт
именно его, закреплённый тегом `0.23.4`, а не `latest`: zig и cargo-zigbuild
приезжают вместе с образом, и если взять `latest`, обе версии перестают быть
нашим решением. Rust в нём старее того, что требует манифест, поэтому каждое
задание сперва ставит stable.

## 8. Как выпускается релиз

Источник истины — версия крейта, тег идёт следом за ней, а не наоборот:

```bash
# 1. Поднять version в [package] у Cargo.toml, затем обновить лок.
cargo check
# 2. Закоммитить это отдельно.
git commit -am "chore: release 0.2.0"
# 3. Поставить тег с тем же числом и ведущим v.
git tag v0.2.0
git push && git push --tags
```

Тег запускает `.github/workflows/release.yml`, который откажется идти дальше,
если эти два числа разошлись: ниже по цепочке `Cargo.toml` никто не читает, и
без такой проверки несовпавший тег выпустил бы бинарник, чей `--version`
противоречит релизу, в котором он приехал. Дальше в релиз кладутся шесть
бинарников, их чексуммы и заметки из коммитов с прошлого тега, а образ
публикуется как `0.2.0`, `0.2`, `0` и `latest`.

Версии семантические. До 1.0 ломающее изменение поднимает минорную — на этом
этапе проект сейчас и находится.
