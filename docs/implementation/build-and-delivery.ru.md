# Сборка и доставка

[English](build-and-delivery.md) | **Русский**

Одна машина собирает под все платформы. Остальные машины получают бинарники, а
не исходники.

## 1. Что нужно

На сборочной машине:

- Rust через `rustup`, не ниже версии из `rust-version` в `Cargo.toml`.
- `zig` и `cargo-zigbuild` (`brew install zig cargo-zigbuild`). zig даёт
  линковщик и libc для каждой цели, больше ничего не требуется.
- `go-task` (`brew install go-task`), чтобы запускать задачи по имени.
- Цели: `task cross:setup`.

На целевых машинах — ничего. В этом и смысл.

## 2. Почему zig, а не альтернативы

`mingw-w64` и zig — не равноценный выбор. zig содержит mingw-w64 для своей
windows-цели и добавляет сверху Linux с нижней границей glibc. Один mingw
покрывает половину задачи.

`cross` работает через Docker. На macOS это виртуальная машина с медленным
доступом к файлам, то есть противоположность быстрому локальному циклу. `cross`
остаётся лучшим ответом там, где важно побайтовое совпадение с CI.

zig линкует через lld, не требует контейнера и не трогает кеш cargo.

## 3. Сборка

```bash
task cross:all        # три платформы
task cross:linux      # x86_64-unknown-linux-gnu.2.28
task cross:windows    # x86_64-pc-windows-gnu
task cross:macos      # aarch64-apple-darwin
```

Суффикс `.2.28` у linux-цели — это самая старая версия glibc, на которой
бинарник пойдёт. Он часть имени цели, а не отдельный ключ.

Читается это наоборот интуиции. Совместимость у glibc обратная, но не прямая,
так что собранное против новой версии на старой не запустится. Линковщик пишет
версию рядом с каждым взятым символом — например `memcpy@GLIBC_2.14`, а не
`memcpy` — и берёт самую новую, какую даёт машина сборки. zig вместо этого
подкладывает свои заголовки и заглушки, и они держат все символы не выше
указанной границы.

Чем ниже цифра, тем шире охват. Поднятие только отрезает дистрибутивы. 2.28 —
это RHEL 8 и его пересборки, поддержка до мая 2029, а ничего старше обновлений
уже не получает.

**Linux-машина собирает любую цель**, включая macOS. Это как раз неочевидный
случай: zig несёт заглушки libc для macOS и подписывает результат ad hoc, без
чего Apple Silicon бинарник убивает. Поэтому одного раннера достаточно, чтобы
выпустить все артефакты, а это важно там, где раннеров Windows и macOS нет.

## 4. Доставка

```bash
task ship:linux
task ship:windows
```

Адреса машин берутся из окружения или из локального `.env`, который `.gitignore`
держит вне репозитория.

Каждая задача копирует бинарник в отдельный каталог на удалённой машине и
запускает его там. Поэтому успешная задача означает бинарник, который на этой
машине работает, а не который просто доехал.

Отдельный каталог — не украшение. Голое имя вроде `onion-gen` может столкнуться
с деревом исходников того же имени, и тогда `scp` запишет бинарник внутрь него.

## 5. Проверка на Windows без Rust на машине

`cargo zigbuild --release --tests --target x86_64-pc-windows-gnu` собирает
исполняемые тесты. Скопируйте их туда и запустите.

Так идут все тесты. Ни один из них не вызывает посторонних программ, поэтому
ни интерпретатора ставить не нужно, ни пути, зафиксированного при сборке,
который на другой машине не найдётся.

## 6. Непрерывная интеграция

`.github/workflows/ci.yml` прогоняет форматирование, clippy и тесты нативно на
Linux, Windows и macOS. Бинарники он собирает на одном linux-раннере, кроме
macOS: `wgpu` линкует фреймворки Apple, которых нет ни в одном другом SDK,
поэтому их собирает мак. `.gitlab-ci.yml` делает остальное только на
linux-раннерах, что возможно, потому что zig собирает оттуда любую цель.

Оба пайплайна собирают CUDA-ядро отдельным заданием и передают PTX ниже
артефактом. Каждое задание ниже выставляет `ONION_GEN_KERNEL_PTX` и остаётся на
stable. Без этого сборочный скрипт собирал бы ядро заново в каждом задании —
один и тот же PTX несколько раз и столько же шансов получить разный.

Образ упаковывается из бинарников, а не компилируется заново. Оба пайплайна
собирают все шесть один раз через zig, а потом отдают два linux-овых
`Dockerfile.dist`, в котором ступени компиляции нет. `Dockerfile` собирает из
исходников и нужен для локальной сборки. В обоих случаях обе архитектуры
получаются с одного amd64-раннера без эмуляции: единственные стадии, которые
что-то выполняют, закреплены за `$BUILDPLATFORM`, а публикуемая только копирует
файлы.

На GitHub это buildx. На GitLab — rootless BuildKit через
`buildctl-daemonless.sh`, которому не нужен ни привилегированный раннер, ни
docker-in-docker. Оба подписывают опубликованный образ по digest через cosign,
без ключа.

Workflow для GitHub прогонялись. **`.gitlab-ci.yml` — нет**, потому что
удалённого на GitLab пока не существует. Это корректный YAML и не более.
Подпись без ключа там к тому же требует gitlab.com: Fulcio не признаёт
self-managed инстанс как издателя, поэтому задание переходит на ключ или
пропускается, как описано в его комментариях.

Одна деталь иначе укусит. Официальный образ `cargo-zigbuild` несёт zig 0.16.0,
Rust 1.93.0 и cargo-zigbuild 0.23.4 — это мы проверили запуском. GitLab берёт
этот образ, закреплённый на `0.23.4`, а не на `latest`, потому что zig и
cargo-zigbuild приезжают вместе с образом, и `latest` забрал бы обе версии из
наших рук. Rust в нём старее того, что требует манифест, поэтому каждое задание
сперва ставит stable.

## 7. Версии, на которых это делалось

zig 0.17.0, cargo-zigbuild 0.23.4, rustc 1.99.0, go-task из Homebrew.

## 8. Как выпускается релиз

Источник истины — версия крейта, и тег идёт следом за ней. Никогда не наоборот.

```bash
# Поднимите version в [package] у Cargo.toml, затем:
task release
```

`task release` читает версию из `Cargo.toml`, обновляет лок, коммитит только
`Cargo.toml` и `Cargo.lock`, ставит тег на этот коммит и пушит оба. Он
отказывается работать, если тег уже есть и если в дереве лежат посторонние
отслеживаемые изменения. Перед пушем он спрашивает, а `CONFIRM=yes` этот вопрос
пропускает.

Те же шаги руками:

```bash
cargo check
git commit -am "chore: release 0.2.0"
git tag v0.2.0
git push && git push --tags
```

Тег запускает `.github/workflows/release.yml`. Этот workflow отказывается идти
дальше, если тег и `Cargo.toml` разошлись. Ниже по цепочке `Cargo.toml` никто не
читает, и без такой проверки несовпавший тег выпустил бы бинарник, чей
`--version` противоречит релизу, который его привёз.

Дальше в релиз кладутся шесть бинарников, их чексуммы и заметки из коммитов с
прошлого тега. Образ публикуется как `0.2.0`, `0.2`, `0` и `latest`.

Версии семантические. До 1.0 ломающее изменение поднимает минорную — на этом
этапе проект сейчас и находится.
