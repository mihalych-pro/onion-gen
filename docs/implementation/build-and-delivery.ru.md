# Сборка и доставка

[English](build-and-delivery.md) | **Русский**

Одна машина собирает под все три платформы; остальные получают бинарники, а не
исходники.

## 1. Что нужно

На машине сборки:

- Rust через `rustup`, не ниже версии из `rust-version` в `Cargo.toml`.
- `zig` и `cargo-zigbuild` (`brew install zig cargo-zigbuild`). zig даёт
  компоновщик и libc под каждую цель, больше ничего не требуется.
- `go-task` (`brew install go-task`), чтобы запускать задачи по имени.
- Цели: `task cross:setup`.

На целевых машинах — ничего. В этом и смысл.

## 2. Почему zig, а не альтернативы

`mingw-w64` и zig — не равные варианты: zig содержит mingw-w64 для своей
windows-цели и сверх того даёт Linux с нижней границей версии glibc. Один
mingw закрыл бы половину задачи.

`cross` работает через Docker, которого на машине сборки не было запущено, а на
macOS это ещё и виртуальная машина с медленным доступом к файлам — прямая
противоположность быстрому локальному циклу. Он остаётся лучшим ответом там,
где нужна побитовая повторяемость с CI.

zig линкует через lld, не требует контейнера и не мешает кешированию cargo.

## 3. Сборка

```bash
task cross:all        # все три платформы
task cross:linux      # x86_64-unknown-linux-gnu.2.17
task cross:windows    # x86_64-pc-windows-gnu
task cross:macos      # aarch64-apple-darwin
```

Суффикс `.2.17` у linux-цели — это самая старая версия glibc, на которой
бинарник пойдёт; он часть имени цели, а не отдельный ключ.

Все три собраны на `darwin/arm64` и запущены каждая на своей машине: linux на
Debian 13, windows на Windows 11 вне WSL, macos обратно на Apple Silicon.
Каждая сама определила AVX2 или NEON и нашла адрес.

**Linux тоже собирает все три**, включая неочевидную цель под macOS: zig несёт
заглушки libc для macOS и подписывает результат ad hoc, без чего Apple Silicon
бинарник бы убила. Поэтому одного раннера достаточно, чтобы выпустить все
артефакты, — что важно там, где раннеров под Windows и macOS нет.

## 4. Доставка

```bash
task ship:linux
task ship:windows
```

Адреса машин берутся из окружения или локального `.env`, который закрыт
`.gitignore`. Каждая задача кладёт бинарник в отдельный каталог на удалённой
машине и там же его запускает, так что успешная задача означает работающий
бинарник, а не просто скопированный.

Отдельный каталог здесь не прихоть: доставка под голым именем `onion-gen`
столкнулась с одноимённым каталогом исходников, и `scp` записал бинарник
внутрь него.

## 5. Тесты под Windows без установки Rust

`cargo zigbuild --release --tests --target x86_64-pc-windows-gnu` собирает
тестовые исполняемые файлы; их достаточно скопировать и запустить. Так нативно
проходят 109 тестов.

Один тест запуститься не может: `end_to_end` зовёт Python-верификатор по пути,
зашитому при сборке, а на другой машине его там нет. Теперь он пропускается с
сообщением вместо падения, и сообщение именно печатается, а не проглатывается
— тест, который молча ничего не проверяет, хуже падающего.

## 6. Непрерывная интеграция

`.github/workflows/ci.yml` прогоняет форматирование, clippy и тесты нативно на
Linux, Windows и macOS и собирает все три бинарника на одном linux-раннере.
`.gitlab-ci.yml` делает то же только на linux-раннерах, что возможно как раз
потому, что zig собирает оттуда любую цель.

Обе конфигурации написаны, YAML в них корректен. **Ни одна не проходила
реального прогона**: у репозитория пока нет удалённых. Доверять им до этого
нельзя.

Одна деталь, которая иначе укусит: официальный образ `cargo-zigbuild`
закрепляет тулчейн старее того, что требует манифест, поэтому каждое задание
сперва ставит stable.

## 7. Версии, на которых это делалось

zig 0.17.0, cargo-zigbuild 0.23.4, rustc 1.99.0, go-task из Homebrew.

**Пара версий связана жёстче, чем кажется.** Нынешний Rust при линковке под
aarch64 выдаёт `--fix-cortex-a53-843419`, и отбрасывает этот аргумент
`cargo-zigbuild`, а не zig. С версией 0.20.1 сборка под arm64 падает с
`unsupported linker arg`, под amd64 проходит — то есть ломается половина целей,
и только одна. Отсюда точное закрепление обеих версий в образе и в CI.

Официальный образ `cargo-zigbuild` для этого не годится: он несёт zig 0.13 и
Rust 1.87, и та же половина целей на нём не собирается.

## 8. Непрерывная интеграция: написана, но не прогонялась

Обе конфигурации лежат в репозитории, и их содержание опирается на проверенное
руками: раннеров одной платформы достаточно, чтобы выпустить все три бинарника,
а образ `cargo-zigbuild` закрепляет тулчейн старее того, что требует манифест,
поэтому каждое задание сперва ставит stable. Каждое задание, собирающее крейт,
ещё и забирает тулчейн ядра: сборочный скрипт компилирует GPU-ядро в PTX — на
раннере без CUDA, а это то свойство, которое легче всего потерять по
недосмотру.

Сборка образа делает это один раз, отдельной стадией: PTX не зависит от
архитектуры, поэтому одной компиляции хватает на обе архитектуры образа, а
правка хост-кода оставляет этот слой в кэше. Стадия передаёт файл сборочному
скрипту через `ONION_GEN_KERNEL_PTX` — потому самой компилирующей стадии
nightly и не нужен.

**Реального прогона не было ни разу.** Удалённых репозиториев у проекта нет, и
по решению владельца они появятся в конце. До тех пор эти файлы — план, а не
факт, и помечены именно так, а не засчитаны сделанными.
