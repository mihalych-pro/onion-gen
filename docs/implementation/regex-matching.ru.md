# Регулярные выражения

[English](regex-matching.md) | **Русский**

Этот документ описывает шестую форму матчинга и структуры, которые держат её
дешёвой.

## 1. Дорого стоит кодирование, а не движок

Дорогая часть этой формы — не движок регулярных выражений. Это шаг, на котором
мы уходим с уровня битов к тексту. Получить base32-кодировку кандидата стоит
намного дороже любой проверки совпадения, работающей по упакованному ключу.

Отсюда и вся форма. Цель не в том, чтобы ускорить движок. Цель — **не доходить
до него вовсе**.

## 2. Три пути и что их разделяет

Программа извлекает из выражения литералы, которые обязана содержать любая
принимаемая строка. Она пользуется `regex_syntax::hir::literal::Extractor` и
берёт набор литералов, а не один литерал:

```text
^abc                          → ["abc"]
^my(shop|store)               → ["myshop", "mystore"]
(cat|dog)food                 → ["catfood", "dogfood"]
^ab.*cd$                      → ["ab"]
^[bcdfghjklmnpqrstvwxyz]{6}   → нет
```

Из этого следуют два независимых вопроса.

**Что отвергает кандидата.** Привязанное выражение отдаёт литералы как
префиксы, и программа сравнивает их прямо с упакованным ключом, ничего не
кодируя. Непривязанное отдаёт подстроки. У них нет фиксированной позиции для
сравнения, поэтому отказ происходит по тексту. У выражения без обязательного
литерала отказа нет вовсе.

**По какому тексту идёт движок.** Движок идёт по 49 символам, которые даёт
ключ, если выражение привязано, ограничено по длине и не содержит оглядок,
кроме `^`. Иначе он идёт по полному адресу, а это один `SHA3-256` на кандидата.

Последнее условие — это белый список, а не перечень опасных оглядок. Текст
ключа — префикс адреса, поэтому `$` и `\b` читают их по-разному. Перечень
опасных конструкций возложил бы на нас обязанность придумать их все и
продолжать придумывать. Та, которую мы не перечислили бы, не упала бы громко.
Она тихо погнала бы движок не по тому тексту.

## 3. Длинные списки литералов получают битмап

Набор литералов выше порога уходит в `BitmapIndex` — ту же структуру, которой
пользуется словарь префиксов. Здесь второй вызывающий, а не вторая реализация.

Порог — 16 литералов, константа `REGEX_BITMAP_FROM`. Ниже него выигрывает прямое
сравнение: несколько сравнений байтов с ключом, который уже в регистре,
быстрее загрузки из таблицы, которой там нет.

Поэтому выражение с обязательным литералом стоит примерно столько же, сколько
префикс, и это верно даже когда выражение дотягивается до контрольной суммы.
Дорогими остаются ровно два случая, и оба дороги по своей природе:

- выражение без литерала, потому что движок тогда видит каждого кандидата;
- непривязанное выражение, потому что у подстроки нет фиксированной позиции,
  по которой можно отказать.

## 4. Корректность: истина — само выражение

Скорость этой формы держится на риске. Программа извлекает литерал из выражения
и отвергает по нему кандидата до запуска движка. Ошибка в извлечении
проявляется не замедлением. Она проявляется ключами, которых программа молча
никогда не находит: скорость не меняется, вывод просто беднее, чем должен быть,
и заметить это можно, только уже подозревая.

Поэтому истина здесь — не вторая наша реализация, а само выражение, применённое
к готовому адресу, в `tests/regex_prefilter_is_sound.rs`. Тестов два:

- **контрактный** читает `Literals` наивно и проверяет, что обещание держится,
  на 41 выражении и 1 000 000 адресов;
- **продуктовый** гоняет тот же набор через матчер со всеми его сокращениями:
  литералы, читаемые по битам, общий префикс и решение по 49 символам.

Оба теста запускаются против намеренно сломанного кода и его ловят:

| Что сломано | Пропущено | Выдумано |
|---|---:|---:|
| литерал не привязан к позиции | 47 110 | 0 |
| убран белый список оглядок | 0 | 44 |
| общий префикс вычислен неверно | 6 726 | 0 |
| убран отказ по литералу до адреса | 3 404 | 0 |

Два свойства этого набора сделаны намеренно. В нём есть выражения, бьющие по
границе между текстом ключа и полным адресом: набор без них не увидит убранного
белого списка. В нём же искомые слова подсажены в ключи, потому что `^shop.*`
встречается примерно раз на миллион адресов, и сломанный отказ дал бы сигнал, не
отличимый от случайности.

## 5. Тест обязан идти через настоящую точку входа

`has_patterns()` решает, в каком цикле пойдёт набор фильтров. Набор с выражением
не должен попасть в цикл, написанный для литеральных префиксов, потому что тот
цикл спрашивает только сравнение байтов.

Тест, вызывающий точки входа матчинга напрямую, такой ошибки не увидит. Выбор
цикла происходит один раз на пачку и лежит вне матчинга. Поэтому
`tests/regex_matching.rs` идёт через `run::run` — ту самую точку входа, которой
пользуется бинарник.

## 6. Устройство помогает выражению мало

Программа отдаёт устройству одну структуру — префиксный битмап, единственную без
указателей внутри. По нему устройство и отсеивает кандидатов.

Выражению отдавать нечего. Поэтому хост разбирает всё, что производит
устройство, и хост становится пределом. В этом отношении выражение ведёт себя
как `contains:`, а не как префикс, хотя на процессоре оно быстрее, чем
`contains:`.

## 7. Чего не сделано и почему

- **Достижимость решается не полностью.** Программа отвергает обязательный
  литерал вне base32, но только когда недостижима каждая ветка, так что
  `^(abc|0xy)` выживает. Она также отвергает требуемую длину больше 56 и
  выражение, не принимающее ничего. Всё остальное уходит в поиск. Живой пример
  границы: `regex:^[a-z]{4}2.*7d$` недостижим, потому что в позиции 54 протокол
  допускает только `{a,i,q,y}`, и дешёвая проверка этого не ловит.
- **Предел «1.5x на тысяче фильтров» выражения не покрывает.** Словарь из тысячи
  регулярных выражений — не тот случай, ради которого эта форма существует, и
  диагностика говорит об этом прямо, а не оставляет подразумеваемым.
- **Unicode выключен.** Стог сена — это 56 байт base32, поэтому `.` означает
  один символ, а `\w` — ASCII. С включённым Unicode оба означают другое, и
  разница вылезла бы фильтром, который тихо совпадает не с тем.
- **Для набора с выражением ожидание — это граница, а не число.** Доля адресов,
  с которыми совпадает выражение, из его текста не следует. Программа держит
  «нельзя оценить» отдельно от «не совпадёт никогда»: это противоположные
  новости.

## 8. Как эту форму меряет скрипт приёмки

`scripts/bench/run-form-acceptance.sh` меряет для выражений три строки, а не
одну: `regex-bits`, `regex-address` и `regex-open`. Это три пути из раздела 2.
Одно число для «regex» усреднило бы три разные стоимости в величину, не
описывающую ни одну из них.
