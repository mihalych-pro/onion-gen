# Пример: onion-сервис на сгенерированных ключах (tor + nginx)

[English](README.md) | **Русский**

Рабочая связка из двух контейнеров: `tor` поднимает onion-сервис на ваших
ключах, `nginx` отдаёт сайт. Наружу ничего не публикуется — сайт доступен
только через Tor.

## Состав

```
docker-compose.yml           tor + nginx
docker-compose.offline.yml   оверрайд для проверки без выхода в сеть Tor
tor/Dockerfile               образ с tor
tor/entrypoint.sh            подготовка каталогов и запуск от пользователя tor
tor/torrc                    конфигурация сервиса
tor/torrc.offline            то же плюс DisableNetwork 1
nginx/onion.conf             server-блок для onion-адреса
site/index.html              демонстрационная страница
keys/                        СЮДА кладутся ключи (в git не попадает)
```

## Запуск

### 1. Положить ключи

Из каталога, который выдал генератор, нужен один файл:

```bash
mkdir -p keys
cp /путь/до/abcd1234….onion/hs_ed25519_secret_key keys/
```

Достаточно только секретного ключа: tor сам выведет из него публичный ключ и
`hostname`. В логе это видно строкой
`Found secret key but not hs_ed25519_public_key. Regenerating.`

Каталог `keys/` перечислен в `.gitignore` — секретный ключ не должен попасть
в репозиторий.

### 2. Проверить, что смонтирован нужный ключ

Прежде чем публиковать сервис в сеть, убедитесь, что адрес тот самый:

```bash
docker compose -f docker-compose.yml -f docker-compose.offline.yml up -d --build
docker compose exec tor cat /var/lib/tor/hs/hostname
```

Выведенный адрес обязан совпасть с именем каталога, который выдал генератор.
В этом режиме включён `DisableNetwork 1`: tor читает ключ и создаёт `hostname`,
но **не объявляет сервис** в сети Tor.

```bash
docker compose -f docker-compose.yml -f docker-compose.offline.yml down
```

### 3. Поднять по-настоящему

```bash
docker compose up -d --build
docker compose logs -f tor
```

Ждите `Bootstrapped 100%`. После этого адрес открывается в Tor Browser.

Проверка из командной строки, если есть локальный Tor-клиент на 9050:

```bash
curl --socks5-hostname 127.0.0.1:9050 \
  "http://$(docker compose exec -T tor cat /var/lib/tor/hs/hostname)/"
```

## Как это устроено

**Ключи монтируются, а не копируются в образ.** Секрет, попавший в слой
образа, расползётся по всем, кто этот образ вытянет, и останется в истории
реестра даже после «удаления». Том смонтирован на чтение (`:ro`), контейнер
копирует ключ к себе в `/var/lib/tor/hs` и выставляет владельца — исходный
каталог не изменяется.

**tor работает не от root.** `entrypoint.sh` готовит каталоги и передаёт
управление пользователю `tor` через `exec su`.

**`DataDirectory` тоже отдаётся пользователю `tor`.** Именованный том
создаётся от root, и без `chown` tor падает с
`Couldn't create private data directory`. Это не теоретическая придирка —
на этом примере ошибка воспроизвелась при первой сборке.

**Порт наружу не публикуется.** У сервиса `nginx` стоит `expose`, а не `ports`:
если открыть порт на хост, тот же контент станет доступен напрямую по IP
сервера, и связь onion-адреса с вашей машиной устанавливается тривиально.

**Отдельный access-лог для onion.** Смешивать onion-трафик с клирнетом в одном
логе — значит связывать эти два сервиса между собой.

## Замена демонстрационного сайта

Положите свои файлы в `site/` либо замените `nginx` на своё приложение и
поправьте `HiddenServicePort` в `tor/torrc`:

```
HiddenServicePort 80 myapp:3000
```

Приложение должно слушать внутри compose-сети и не публиковать порт на хост.

## Проверено

Связка проверена на этой конфигурации: tor 0.4.9.11 в `alpine:3.20`,
`nginx:1.27-alpine`, запуск в офлайн-режиме. tor вывел ровно тот адрес, что
дал генератор, nginx отдал страницу.

Сквозная проверка с реальной публикацией дескриптора в сети Tor **не
проводилась** — она требует объявить сервис наружу.
